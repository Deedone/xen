# Xen Heap Allocations -- Minerva Analysis

At _runtime_, all domains can perform allocations from a shared Xen heap.
This entails potential predictability, safety/security problems since (less
critical) domains might starve Xen-heap allocations performed by (higher
critical) domains.

We use compiler-support to generate call-graphs and an statically analyze the
paths leading to specific allocation functions.

Here we focus on `alloc_domheap_pages()`, since it is one of the main allocator
function for domains requests and also for the Xen heap ones, since it's in turn
called by `alloc_xenheap_pages()`.

```
void *alloc_xenheap_pages(unsigned int order, unsigned int memflags)
{
    struct page_info *pg;
    <...>
    pg = alloc_domheap_pages(NULL, order, memflags | MEMF_no_scrub);
```

We are interested in identifying the possible call paths that lead to a
`alloc_domheap_pages()` call with `NULL` parameter as domain (this is trivially
the case for `alloc_xenheap_pages()`), and also understand what are the changes
required in the xen codebase if we explicitly pass a domain pointer to the
allocation function.
Also, how the information must be passed down the call chain.

The analysis is composed by one offline call-path analysis that identifies all
the upcall graphs leading to a specific function (e.g., `alloc_xenheap_pages()`,
or `alloc_domheap_pages()`), and an online analysis (See
[Online](#online-call-stack-generation)), that aims to dynamically generate the
call-path using dedicated `WARN()` calls inserted in the code.

## Offline call paths analysis

Given the large amount of call paths, the offline analysis uses scripts that
scan the compiler generated call-graph and can filter out selected paths that
are deemed not of interest for the analysis (See
[Excluded functions](#excluded-functions)).

The analysis explores the call graph info files generated by GCC
`-fcallgraph-info` flag using the Python script `callpath.py`.
The `CONFIG` options used during the compilation phase restrict the call-graph
that need to be explored.

To reproduce the results, first you need to add the `-fcallgraph-info` to Xen
build commands to produce `.ci` files.
Then you can run the following:

```
./callpath.py to <path-to-xen> alloc_domheap_pages -i -e minerva_analysis/excluded_functions > output
```

Please note that:

- recursive paths aren't taken into account.
- call location is ignored.
  If a function calls another one multiple times, the edge that connects the two
  functions is visited only once.
- dynamic calls such as function pointer calls are not taken into account.
- many functions are excluded from the path generation since they don't match
  safety certification use case constraints.
  The file `excluded_functions` contains such functions.
  See [Excluded functions](#excluded-functions) for more information on how it's
  obtained.
- `__domain_crash()` is also excluded since it's in the fail path and it's
  presence lead to the explosion of the total number of paths (76 MiB of data
  against 30+ GiB in x86 case).

### Refining the initial call tree

The call tree supports the identification of call path that potentially
constitute a "dangerous" allocation (and that require further investigation) or
that can be excluded from the analysis because e.g. they don't belong to the
usage-domain, or because the allocation can be converted to a per-domain
allocation.

To remove paths from the call graph, the `filter.py` script removes the
functions that are deemed as "not dangerous".

1. First we identify a function that is common to a group of paths in the
   callpath file.
1. We analyze the code (see Arm64 and x86 sections).
1. We remove the given function from the callpath using the `filter.py` script.
   ```
   filter.py xen_{arm64|x86}_callpath -i <function1> <function2> ...
   ```
   This generates a smaller callpath file where paths are removed if they
   contain one of the functions passed as input.
   We start again with 1.
   until no more paths are present.

`filter.py` is actually capable of both whitelist and blacklist filtering.
It's up to the user to decide what kind of filter to use.

Every artifact used by or produced by the analysis can be found inside
`minerva_analysis/` folder (those include `callpath.py` and `filter.py`).

### Excluded functions

`excluded_functions` is the list of functions that has been excluded "by
default" from the path analysis because have been deemed (via multiple calls) to
be outside the usage-domain.
In brief, the usage-domain excludes:

- Dom0 calls
- hypercalls to generate other VMs
- PV guests

The list therefore contains:

- hypercalls with the exception of grant table and event channel operations
- `__init` functions

VirtIO operations, io requests, serial emulation are instead in scope.

The `excluded_functions` file contains both Arm64 and x86 functions.
In particular:

- hypercalls are taken from `xen/include/public/xen.h` by replacing
  `__HYPERVISOR` with `do` to produce the actual function names.
  `do_event_channel_op_compat`, `do_grant_table_op` `do_event_channel_op` are
  removed from the list.
  For the x86 case, the generated file `xen/include/xen/hypercall-defs.h`
  contains all hypercalls.

- init functions are found with the following command:

  ```
  rg -uuu "__init .*\(" -t c -t h -o xen -N --no-heading -I
  ```

  where `rg` is `ripgrep`.
  This gives a list of all the init functions, but it requires manual
  intervention to remove duplicates, leftovers like types, spaces, other
  attributes etc.

## Static analysis of selected functions

Among the paths identified leading to `alloc_domheap_pages()` with domain
parameter set to `NULL`, we identified and report an initial list of entry point
/ sub-tree functions that either require further attention or that could be
excluded from the call-tree.
Further analysis and validation from the maintainer of the respective call-trees
is obviously required.

### Arm64

#### `alloc_xenheap_pages()`

This is the main Xen heap allocator function and it calls
`alloc_domheap_pages()` with the domain parameter set to `NULL`.
More than two thirds of the found paths eventually call this function.

Instead of `NULL` (which would result in an "unnamed" allocation from the shared
Xen heap), `current->domain` could be used to get the domain Xen has paused.
Further discussion in the design section
([Design](#design-of-per-domain-xen-heap-solution)).

#### `vcpu_create()`

Just a single path:
the one that calls `vmtrace_alloc_buffer()` (this function isn't directly
reported in `xen_arm64_callpath` because of inlining).
In this case `alloc_domheap_pages()` is called with the running domain as the
parameter, so it's already a per-domain allocation.

#### `vmap()`

The only caller of this function is in `xen/common/argo.c`.

#### `vmap_contig()`

There are no callers of this function in the use case scenario.

#### `vmalloc_type()`

These paths should always come from a `__init` function, except for the
livepatch support which is currently excluded from the use case scenario.
The fact that they still appear in `xen_arm64_callpath` is not entirely clear,
but they should never happen.

#### `__vmap()`

Given what has been said in the above sections, the remaining to-be-discussed
callers are the following:

- `enable_spectre_bhb_workaround()`
- `sunxi_reset()`
- `rpi4_reset()`
- `xgene_storm_reset()`

which should be further discussed to understand if they are actually called
after boot.
(***TODO***)

#### `p2m_alloc_page()`

P2M tables are per-domain by definition, but in case of the hardware domain (aka
`dom0`) this comment applies:

```C
/*
 * For hardware domain, there should be no limit in the number of pages that
 * can be allocated, so that the kernel may take advantage of the extended
 * regions. Hence, allocate p2m pages for hardware domains from heap.
 */
```

With the recent cache coloring patch series from Minerva Systems (see this
[commit](https://gitlab.com/xen-project/xen/-/commit/891f077a71aa1ce45adc43f114a02768565dc14b)),
the allocation is done using memory from the hardware domain, so this is not a
problem.

#### `p2m_set_allocation()`

This single path happens on domain destroy and it doesn't lead to new
allocations since the function is called to free pages (the path is still
reported because our analysis scripts can't understand logic flow).

#### `xen_pt_update()`

Given what has been said in the above sections, the remaining to-be-discussed
callers are the following:

- `enable_nonboot_cpus()` which is never actually called.
- `destroy_xen_mappings()` and `modify_xen_mappings()` which don't need to
  allocate new tables, but rather modify or free already allocated ones.

### x86

#### `alloc_xenheap_pages()`

This function is common to all architectures, so the analysis is the same as for
Arm64.

#### `gnttab_transfer()`

It allocates pages for the destination domain using its memory so there is no
problematic allocation here.

## DEBUG: prototyping of per-domain Xen heap solution

The set of scripts and the call trees provided in this analysis defines a
potential way of tackling this problem by converting most of the allocations
("anonymous allocations") that insist on the global Xen heap into a per-domain
one.
The (already available) per-domain heaps are given an additional amount of
memory that is used for Xen heap allocations, increasing predictability and
safety since the Xen heap isn't shared anymore.

The focus (use case scenario) is on allocations performed at runtime (i.e.,
after the init phase is concluded) and with the static variants
(dom0less/hyperlaunch) of Xen configurations.

The previous analysis highlighted that `alloc_xenheap_pages()` is one of the
main entry points for 'anonymous' allocations.
Therefore, switching this function to use per-domain allocations instead of
anonymous ones will trigger many fall-out configuration changes and needs for
increase in e.g., per-domain allocation sizes that might be considered for
further analysis.

A debug-solution to test the consequences of updating allocations to per-domain
ones is to enforce a domain inside `alloc_xenheap_pages`.
The current domain is in many cases a sound choice for prototyping purposes.

`current->domain` can be used to retrieve the running domain, but `current` is
initialized only after domain creation (and of course, the allocations before
domain initialization are rightfully done from the single xen heap).
To avoid dereferencing a null pointer, we can simply check that `system_state`
has reached `SYS_STATE_active`.
This change can be found in `common/page_alloc.c`.

```diff
-    pg = alloc_domheap_pages(NULL, order, memflags | MEMF_no_scrub);
+    if (system_state == SYS_STATE_active)
+        d = current->domain;
+
+    pg = alloc_domheap_pages(d, order, memflags | MEMF_no_scrub);
```

The changes implemented in the `minerva/per-domain-xenheap-idea-approach` branch
enact this approach.
*NOTE*:
the changes are not correct under all possible scenarios (clearly enforcing the
current domain is _NOT_ correct in many cases), but this allowed the
identification of further configuration updates that might be needed.

Now that Xen heap pages are assigned to a domain, we encounter a very basic
problem regarding page counters.

A domain has 3 basic page counters (it has more actually, but they're more
sophisticated and not relevant now):

- `max_pages`:
  it's the upper limit and it's normally equal to the domain assigned memory
  (e.g. `dom0_mem` param for Dom0).
- `tot_pages`:
  it's the current assigned number of pages and it's normally equal to
  `max_pages`, unless `MEMF_no_refcount` flag is used during allocation, in
  which case it's greater.
  It's incremented by `assign_pages()`.
- `extra_pages`:
  it's the counter for non referenced counted pages.

To check for over-allocation against `max_pages`, the counter used is actually
the expression `tot_pages - extra_pages` returned by `domain_tot_pages()`.
Clearly, trying to allocate pages for the Xen heap using domain memory, triggers
the over-allocation check because `domain_tot_pages()` becomes greater than
`max_pages`.
To solve this issue we propose a very basic solution:

1. Add a new command line parameter that let the user set the Xen heap size
   reserved for Dom0.
1. Add a new device-tree attribute that let the user set the Xen heap size
   reserved for DomUs.
1. At boot time, initialize domains `max_pages` with the memory size plus the
   Xen heap size, so that `d->max_pages += xenheap_pages`.

## Next Steps

- Helper for appropriate size definition of the per-domain Xen heaps.
  Currently 2MiB seems to be ok, but configuration parameters / user-helper
  should be defined (?)
- Extensive online analysis and experimental (e.g., via `WARN`) validation of
  the design (i.e., are there other use-cases that haven't been considered
  yet?).
  Automatically parse the WARN() trace and match it against the static analysis.
  Specifically, this analysis can not automatically identified if the
  allocations accounted to one specific domain are better accounted to a
  different domain (e.g., second level page table allocations to cover
  shared-memory mappings).

## Example: analysis of `alloc_xenheap_pages()`

First we generate `.ci` files by adding the `-fcallgraph-info` to GCC build
commands.
Alternatively we can use [`bear`](https://github.com/rizsotto/Bear) to create a
`compile_commands.json` file that lists the commands needed to generate every
object file.
With that, we can use `callpath.py update` command to automatically generate the
`.ci` files.

```
cd <path-to-xen>
make distclean # required
<copy any .config you want to use in <path-to-xen/xen>
bear -- make dist-xen -j16
./callpath.py update <path-to-xen>
```

We can now create the callpath file:

> In the **x86** case, `__domain_crash` should be added to the excluded
> functions, otherwise the scripts takes a very long time because it generates a
> huge amount of crash-related paths that should be analyzed separatedly if
> deemed in scope.

```
cd minerva_analysis
./callpath.py to <path-to-xen> alloc_xenheap_pages -i -e init_functions > <arch>/alloc_xenheap_pages
```

Then we can refine the callpath file via the `filter.py` script.
If we want to include only the hypercalls we can simply do:

```
./filter.py <arch>/alloc_xenheap_pages -I hypercalls > <arch>/alloc_xenheap_pages_hypercalls
```
